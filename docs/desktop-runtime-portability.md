# 桌面运行环境可替换性

2026-10-19：用户接受当前 Electron 体积，当前继续推进核心功能；后续保留迁移到更轻量桌面方案的空间。尚未选定替代框架，也不为本目标提前重写现有功能或增加第二套运行环境。

## 当前边界

| 位置 | 职责 | 迁移准备 |
|---|---|---|
| `src/shared/model.ts`、`session.ts` | 工程模型、编辑命令、验证、撤销重做 | 保持独立于 Electron、文件系统与 UI；命令和快照是稳定边界 |
| `src/shared/io.ts`、`smartPattern`、`src/legacy` | 工程／NBS 编解码、智能整理 | 输入输出使用数据和字节，不引入宿主句柄、路径访问或原生窗口对象 |
| `StudioAPI` 与 `src/preload/index.ts` | UI 与桌面宿主的能力接口、Electron IPC 适配 | renderer 通过能力接口访问宿主；其他运行环境实现对应适配，不让组件直接引用 Electron |
| `src/main` | 权威工程实例、文件、对话框、剪贴板、原生窗口、跨窗口协调 | 宿主依赖集中于此，文件能力已有可注入存储／对话框；继续保持这些替换点 |
| `src/renderer` | React、Canvas、交互、Web Audio | 不依赖 Node 集成；文件、窗口、剪贴板和宿主消息走能力接口。音频调度尽量与宿主消息传递分开 |

当前 shared／legacy 没有 Electron 或 `node:` 导入；renderer 已通过 `window.studio: StudioAPI` 使用宿主能力。后续功能应维持此边界。

## 后续开发约束

1. 乐理、音符、Pattern、音色映射、格式转换与整理算法继续放在纯数据核心中。宿主异常在能力边界转换，不能让音乐模型保存 Electron 对象或操作系统资源句柄。
2. 新宿主能力先定义明确的输入、结果、错误和生命周期，再在 Electron 层实现。订阅须可取消，异步编辑仍校验工程 generation，防止重开后把旧任务结果写入新工程。
3. 新工程字段保持可序列化与版本兼容；导出不能依赖运行环境特有的缓存或临时路径。资源解析、文件原子写入、未保存保护和 ZIP 校验继续是独立职责。
4. 不把播放时钟绑到窗口帧率或宿主 IPC 到达时间。跨窗口只保留一个播放所有者，关闭、停靠与切换工程的取消语义继续明确。
5. 优先使用宿主无关的布局、Canvas、React 与音频接口；确需特有能力时集中封装。不要仅为将来可能迁移而增加空适配层、双后端或替代运行环境依赖。

## 真正迁移前必须验证

候选可以包括 Tauri 或其他桌面方案，最终选择以原型和测量为准。先用同一工程和机器记录运行包／解压体积、冷启动、空闲内存、大曲编辑延迟和播放时序，再比较候选。

当前 `Session` 的权威实例运行在 Electron 主进程。它虽是 TypeScript 纯数据代码，也不能据此假设换成另一宿主后可原样执行：届时必须决定权威核心的运行位置、跨窗口共享与后台任务模型，或评估核心移植及一致性成本。不能靠继续捆绑完整 Node 运行环境就宣称已经实现轻量迁移。

先验证以下最小闭环，再考虑正式切换：

- `.nbproject` 保存／重开、NBS 读取／导出、撤销与未保存保护。
- 大曲选择、拖动、缩放和智能整理；保持现有音乐事件与导出对照结果。
- 真实音频解码、调音、定时播放、暂停／终止、资源缺失与设备恢复。
- 多窗口编辑、播放所有权、停靠、窗口关闭及异步任务取消。
- 实际文件、剪贴板、路径与资源权限，以及 Windows 分发与升级流程；跨平台能力分别验收。

纯数据测试、浏览器交互测试与真实宿主测试应继续分开。迁移时复用前两类证据，并为新宿主重新跑实际桌面验收。现有用户歌曲库只做本地只读测试，不放入源码仓库。
